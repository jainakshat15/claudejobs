# claudejobs HTTP API

A local HTTP API (FastAPI, bound to `127.0.0.1:8000` by default) for queueing, running and
supervising Claude Code sessions. Two auth schemes share it: `X-Auth-Token` for admin/bot
routes and `X-Job-Token` for the routes a running job calls back on. Every request and
response — but never the headers — is appended to a markdown transcript at `REQUEST_LOG_FILE`
(default `logs/requests.md`, rotated at `REQUEST_LOG_MAX_MB`).

> Examples use a POSIX shell (Git Bash, WSL, Linux, macOS). In PowerShell use `curl.exe` and
> escape the inner double quotes, or use `Invoke-RestMethod`.

## Authentication

| Scheme | Header | Value | Used by |
| --- | --- | --- | --- |
| Admin | `X-Auth-Token` | `API_TOKEN` from `.env` | posters, the CLI, the Telegram/Slack bots |
| Job-scoped | `X-Job-Token` | the token minted when the job was claimed | `run_job` and `jobctl` inside a running job |

**Admin (`X-Auth-Token`)** is a shared secret compared with `secrets.compare_digest`. It fails
closed: if `API_TOKEN` is empty the API answers **503** to every admin route rather than
allowing anything through.

**Job-scoped (`X-Job-Token`)** is a fresh `secrets.token_urlsafe(32)` generated by the
dispatcher at launch. Only its SHA-256 hash is stored, in `jobs.job_token_hash`; the plaintext
is handed to the worker through a per-job launch script (never on a command line). Verification
is `SELECT * FROM jobs WHERE id = %s AND job_token_hash = sha256(token)`, so a job token unlocks
exactly one job and nothing else. The hash is cleared when a job is retried or requeued after a
lease expiry, which invalidates the old token.

`GET /health` takes no auth at all. Every other route requires one of the two headers.

## Job routes (admin)

Job objects are the full `jobs` row with `job_token_hash` removed. Responses below are trimmed
to the interesting fields; the real payload carries every column in the table.

### POST /jobs

Queue a job. Returns **201**.

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `prompt` | string | required | Min length 1. The opening prompt for Claude |
| `directory` | string \| null | `null` | Falls back to `DEFAULT_DIRECTORY`; resolved, must exist, must sit under `ALLOWED_ROOTS` |
| `title` | string \| null | `null` | Max 200 chars; defaults to the first 60 chars of the prompt |
| `model` | string \| null | `null` | Falls back to `DEFAULT_MODEL`, else null |
| `permission_mode` | string \| null | `null` | One of `bypassPermissions`, `acceptEdits`, `auto`, `plan`, `default`; falls back to `DEFAULT_PERMISSION_MODE` |
| `append_system_prompt` | string \| null | `null` | Appended after the queue instructions |
| `priority` | integer | `100` | 1–1000, lower runs sooner |
| `max_attempts` | integer \| null | `null` | 1–10; falls back to `DEFAULT_MAX_ATTEMPTS` |
| `timeout_minutes` | integer \| null | `null` | >= 1; falls back to `JOB_TIMEOUT_MINUTES` when the sweep runs |
| `scheduled_at` | datetime \| null | `null` | Not started before this time; stored as `now()` when null |
| `source` | enum | `"http"` | `http`, `cli`, `telegram`, `slack` |
| `source_user_id` | string \| null | `null` | Chat identity, used by reply routing |
| `source_username` | string \| null | `null` | |
| `source_chat_id` | string \| null | `null` | Required for outbound delivery; without it the job has no chat channel |
| `source_thread_id` | string \| null | `null` | |
| `source_message_id` | string \| null | `null` | |
| `created_by` | string \| null | `null` | Falls back to `source_username` |
| `payload` | object | `{}` | Free-form; `payload.extra_args` (a list) is appended to the `claude` command line |

### POST /jobs/{job_id}/cancel

Immediate if the job is `queued` (straight to `cancelled`, `finished_at` set). Cooperative if
it is `running` or `waiting_input`: `cancel_requested` is set, open questions are cancelled, and
the worker picks it up on its next heartbeat.

| Field | Type | Default |
| --- | --- | --- |
| `reason` | string | `"cancelled by poster"` |
| `actor` | string \| null | `null` |

```bash
curl -s -X POST http://127.0.0.1:8000/jobs/42/cancel \
  -H "X-Auth-Token: $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "wrong branch", "actor": "akshat"}'
```

```json
{"id": 42, "status": "running", "cancel_requested": true, "cancel_reason": "wrong branch", "finished_at": null}
```

### POST /jobs/{job_id}/retry

Only finished (terminal) jobs. Clears the worker fields, token hash, session id, error and exit
code, resets `queued_at`/`scheduled_at` to `now()`, and raises `max_attempts` to at least
`attempts + 1`.

| Field | Type | Default |
| --- | --- | --- |
| `actor` | string \| null | `null` |

```bash
curl -s -X POST http://127.0.0.1:8000/jobs/42/retry \
  -H "X-Auth-Token: $API_TOKEN" \
  -H "Content-Type: application/json" -d '{"actor": "cli"}'
```

```json
{"id": 42, "status": "queued", "attempts": 1, "max_attempts": 2, "worker_id": null, "session_id": null, "error": null, "exit_code": null}
```

Tail of the per-job worker log (`jobs.log_path`, else `LOG_DIR/job-<id>.log`). `tail` defaults



## Job-scoped routes (`X-Job-Token`)

These are what `run_job` and `jobctl` call from inside a running session. The token is read from
`CLAUDEJOBS_JOB_TOKEN` in the job's environment. In the examples below, `$JOB_TOKEN` is that
value.

### GET /jobs/{job_id}/self

The job's own row (token hash stripped). `run_job` calls this first to learn the directory,
model, permission mode, session id and prompt.

```bash
curl -s http://127.0.0.1:8000/jobs/42/self -H "X-Job-Token: $JOB_TOKEN"
```

```json
{
  "id": 42,
  "status": "running",
  "prompt": "Add retry handling to the payments client and run the tests",
  "directory": "D:\\work\\web",
  "model": null,
  "permission_mode": "bypassPermissions",
  "session_id": "0d0c3f7a-1a9d-4b0f-8d1e-7c0a5b2f9e33",
  "timeout_minutes": 90,
  "payload": {}
}
```

### POST /jobs/{job_id}/heartbeat

No request body. Extends `lease_expires_at` to `now() + JOB_LEASE_SECONDS` and sets
`last_heartbeat_at`, but only while the job is `running` or `waiting_input`.

```bash
curl -s -X POST http://127.0.0.1:8000/jobs/42/heartbeat -H "X-Job-Token: $JOB_TOKEN"
```

```json
{"job_id": 42, "status": "running", "cancel_requested": false, "cancel_reason": null}
```

If the job is no longer active (already finished, or reaped by the lease sweep) the update
matches nothing and the route answers 200 with a stop instruction:

```json
{"job_id": 42, "status": "failed", "cancel_requested": true, "detail": "job is no longer active; stop work"}
```


### POST /jobs/{job_id}/notify

| Field | Type | Default |
| --- | --- | --- |
| `message` | string | required, min length 1 |

Records a note **and** queues a chat message to the poster. Jobs with `source` outside

then `false` and `detail` says so.

```bash
curl -s -X POST http://127.0.0.1:8000/jobs/42/notify \

  -d '{"message": "the migration will lock the table for ~30s"}'
```

```json
{"job_id": 42, "delivered": false, "detail": "this job has no chat channel; message recorded only"}
```

### POST /jobs/{job_id}/ask

| Field | Type | Default |
| --- | --- | --- |
| `question` | string | required, min length 1 |

Records a question, moves the job from `running` to `waiting_input`, and queues the question to
the poster's chat. A job may have only one open question at a time (enforced by a partial unique
index): if one is already open, that one is returned instead, nothing new is delivered, and
`reused_open_question` is `true`.

```bash
curl -s -X POST http://127.0.0.1:8000/jobs/42/ask \
  -H "X-Job-Token: $JOB_TOKEN" -H "Content-Type: application/json" \
  -d '{"question": "Should the retry back-off be exponential or fixed?"}'
```

```json
{"job_id": 42, "question_id": 17, "status": "open", "delivered": true, "reused_open_question": false}
```

### GET /jobs/{job_id}/questions/{question_id}

Long-poll. `wait` defaults to `25` seconds and is clamped to 0–60; the handler re-checks the
question every 1.5 s and returns as soon as it leaves `open` or the job has `cancel_requested`.
When the window elapses it returns the same shape plus `"timed_out_waiting": true`, and `jobctl
ask` calls it again.

```bash
curl -s "http://127.0.0.1:8000/jobs/42/questions/17?wait=25" -H "X-Job-Token: $JOB_TOKEN"
```

```json
{
  "job_id": 42,
  "question_id": 17,
  "status": "answered",
  "answer": "exponential, cap at 30s",
  "answered_by": "akshat",
  "cancel_requested": false,
  "job_status": "running"
}
```

Timed-out poll:

```json
{"job_id": 42, "question_id": 17, "status": "open", "answer": null, "answered_by": null, "cancel_requested": false, "job_status": "waiting_input", "timed_out_waiting": true}
```

### POST /jobs/{job_id}/finish

| Field | Type | Default | Notes |
| --- | --- | --- | --- |
| `status` | enum | required | `succeeded`, `failed` or `cancelled` |
| `summary` | string \| null | `null` | Stored in `result_summary` |
| `error` | string \| null | `null` | |
| `exit_code` | integer \| null | `null` | |

The **first terminal state wins**. If the job is already terminal, the reported status is
ignored (an `finish_ignored` event is recorded), only a missing `exit_code` is filled in, and the
existing row comes back. A `cancelled` report on a job whose `cancel_reason` is `timeout` is
stored as `timed_out`. Finishing cancels any open question and queues a summary message to the
poster.

```bash
curl -s -X POST http://127.0.0.1:8000/jobs/42/finish \
  -H "X-Job-Token: $JOB_TOKEN" -H "Content-Type: application/json" \
  -d '{"status": "succeeded", "summary": "added exponential back-off; 34 tests pass", "exit_code": 0}'
```

```json
{
  "id": 42,
  "status": "succeeded",
  "result_summary": "added exponential back-off; 34 tests pass",
  "error": null,
  "exit_code": 0,
  "finished_at": "2026-09-20T10:52:18.223Z",
  "lease_expires_at": null
}
```

```bash
curl -s -X POST http://127.0.0.1:8000/outbound/claim \
```

### POST /outbound/{outbound_id}/sent

Marks the row `sent`, stamps `sent_at`, clears `last_error`, and stores the provider ids — those
are what make a plain "reply to this message" route back to the right question.

| Field | Type | Default |
| --- | --- | --- |
| `provider_message_id` | string \| null | `null` |

Back to `pending` for another attempt, or `failed` once `attempts >= max_attempts` (default 5).

```bash
curl -s -X POST http://127.0.0.1:8000/outbound/108/failed \
```

### POST /replies

Works out which waiting job a human's chat reply belongs to, then answers it.

| Field | Type | Default |
| --- | --- | --- |
| `channel` | enum | required — `telegram` or `slack` |
| `chat_id` | string | required |
| `user_id` | string | required |
| `body` | string | required, min length 1 |
| `username` | string \| null | `null` — used as `answered_by`, falling back to `user_id` |
| `reply_to_message_id` | string \| null | `null` |
| `thread_id` | string \| null | `null` |
| `job_id` | integer \| null | `null` |

Resolution order, most explicit first:

1. an explicit `job_id` (`/reply 42 yes`)
2. `reply_to_message_id` matched against `outbound_messages.provider_message_id`
3. `thread_id` matched against `COALESCE(provider_thread_id, provider_message_id)`
4. the person's only open question

With more than one job waiting and no other signal it refuses with **409** and lists the ids
rather than guessing.

```bash
curl -s -X POST http://127.0.0.1:8000/replies \
  -H "X-Auth-Token: $API_TOKEN" -H "Content-Type: application/json" \
  -d '{"channel": "telegram", "chat_id": "-1001234567890", "user_id": "5551212",
       "username": "akshat", "body": "exponential, cap at 30s", "reply_to_message_id": "9912"}'
```

```json
{
  "job_id": 42,
  "question_id": 17,
  "status": "answered",
  "job_status": "running",
  "question": "Should the retry back-off be exponential or fixed?"
}
```

## Errors

Every error is FastAPI's standard shape:

```json
{"detail": "job #42 is running; only queued jobs can be edited. Cancel it and submit a new one."}
```

| Code | Raised when |
| --- | --- |
| **400** | No `directory` given and `DEFAULT_DIRECTORY` is unset; the path cannot be resolved (`OSError`); the path exists but is not a directory (`POST /jobs`, `PATCH /jobs/{id}`). On `GET /jobs`, a `status` value that is not one of the seven statuses. |
| **401** | Admin routes: `X-Auth-Token` missing, or not equal to `API_TOKEN`. Job routes: `X-Job-Token` missing, or no `jobs` row matches `(job_id, sha256(token))` — including after a retry or lease requeue, which clears the stored hash. |
| **403** | The resolved directory is outside every entry in `ALLOWED_ROOTS` (`POST /jobs`, `PATCH /jobs/{id}`). The message names the roots. |
| **404** | No job with that id (`GET`/`PATCH`/`cancel`/`retry`/`answer`/`messages`/`events`/`log`, and `POST /replies` with an explicit `job_id`). On `answer`: the job has no open question, or the supplied `question_id` belongs to a different job. On `GET /jobs/{id}/questions/{qid}`: no such question for this job. On `outbound/{id}/sent` and `/failed`: no outbound message with that id. On `/replies`: the named job is not waiting for an answer, or nothing matched and the user has no open questions at all. |
| **409** | See below. |
| **500** | `GET /jobs/{id}/log` when the log file exists but cannot be read (`OSError`). |
| **503** | `API_TOKEN` is not configured — every admin route refuses rather than running open. Also any route whose database access raises `ConfigError` (`DATABASE_URL` missing, or the pool cannot reach Postgres), and any malformed setting, via the app-level `ConfigError` handler. The API deliberately starts even when the database is unreachable, so these keep coming back until `.env` is fixed. |

FastAPI/pydantic field validation failures (missing `prompt`, unknown `permission_mode`,
`priority` out of range, bad `status` enum on `finish`) return **422** before any handler runs.

### The 409 cases

| Route | Condition | Message |
| --- | --- | --- |
| `PATCH /jobs/{id}` | The job already started — status is not `queued` | `job #42 is running; only queued jobs can be edited. Cancel it and submit a new one.` |
| `PATCH /jobs/{id}` | It was still queued when read but the guarded `UPDATE` matched nothing | `job #42 started before the edit landed` |
| `POST /jobs/{id}/cancel` | The job is already terminal | `job #42 already finished (succeeded)` |
| `POST /jobs/{id}/retry` | The job has not finished yet | `job #42 is running; only finished jobs can be retried` |
| `POST /jobs/{id}/answer`, `POST /replies` | The question is no longer `open` | `that question is already answered` (or `expired` / `cancelled`) |
| `POST /jobs/{id}/answer`, `POST /replies` | The question closed between the check and the write | `the question closed while you were answering` |
| `POST /jobs/{id}/ask` | The job went terminal before the question landed | `job is cancelled; cannot ask a question` |
| `POST /replies` | The sender has more than one job waiting and gave no job id, reply-to or thread | `3 of your jobs are waiting (#42, #51, #58). Say which one: /reply <job id> <your answer>` |

## Job status values

Seven statuses, from `claudejobs/models.py` (and enforced by a `CHECK` constraint on
`jobs.status`):

| Status | Terminal | Meaning |
| --- | --- | --- |
| `queued` | no | Waiting to be claimed. The only editable status |
| `running` | no | Claimed by a worker and executing. Occupies a slot |
| `waiting_input` | no | Parked on an open question to the poster. Still occupies a slot |
| `succeeded` | **yes** | Finished cleanly |
| `failed` | **yes** | Reported failure, a non-zero exit, a launch error, an unanswered question, or an expired lease with no attempts left |
| `cancelled` | **yes** | Cancelled while queued, or a cancel honoured by the worker |
| `timed_out` | **yes** | Stopped because it passed its wall-clock limit (`cancel_reason = 'timeout'`) |

`queued`, `running` and `waiting_input` are what `?status=active` (or `open`) expands to.
`running` and `waiting_input` are the two that count against `MAX_CONCURRENT_JOBS`.
